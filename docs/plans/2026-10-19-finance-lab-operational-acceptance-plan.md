## 一、总体目标与完成定义

下一阶段的目标，是把已经通过离线校验的恢复候选，经过重新复核、人工确认和正式验收，接入一个独立、稳定、可追溯的运行根；再用真实自然运行证据判断每日任务是否恢复。

工作分成三个结果层次：

1. **候选可验证**：材料身份明确，行情内容可追溯，账本没有损失。这一层已有10月18日证据。
2. **新运行根可验收**：在全新目录形成验收凭据，保持账户身份和原始数据，明确标记离线恢复及数据截止日。这一层尚未执行。
3. **正式自动化可证实**：计划任务实际启动，应用产生完成或失败归档，数据来源结果可核对，账本提交与应处理日期一致。这一层尚未恢复验收。

最终交付不能只写“任务安装成功”或“状态Ready”。应当能回答：代码从哪里加载、数据写到哪里、什么时候启动、哪一步失败、处理了哪些日期、提交了哪些账本事件，以及最后成功证据对应哪个数据集。

整个项目仍用于学习、研究和本地模拟，不接券商、不自动交易。运维恢复不构成策略有效性、收益显著性或真实资金准入证明。

## 四、工作组织与执行纪律

每一项实施任务都使用相同流程：先形成具体计划和验收条件，再执行，随后进行两名独立审查和双方交叉核对，最后更新状态。

执行者负责采集和操作；审核者默认只读本轮归档证据和相关实现，各自写唯一审查记录。独立阶段不阅读另一人的结论，交叉阶段核对结论差异和修正闭环。审核者不自行重跑行情、修改任务或连接正式数据库。

写入产品代码的多人实施须按AGENTS使用独立分支或worktree，并划定文件责任。本轮计划编制不改产品代码；后续文档只读审查顺序进行，各人唯一输出，避免同时编辑同一文件。

发现问题时遵循以下规则：

- 阻断问题先修正或明确停止，再进入下一阶段；不能靠“另一位认为可以”忽略问题。
- 审查通过只覆盖实际展示的证据范围，不能扩大为全系统安全或策略有效。
- 失败记录、旧成功和新尝试分别保存。不得覆盖失败目录或用旧成功冒充本次成功。
- 测试按实际变更选择；仅操作现有恢复工具时优先实际完整性、账本和数据校验，不无故重跑全量压力测试。
- 若必须修改源码，另列最小修复计划、必要测试和双审，不在切换过程中临时扩大改动。

## 五、分阶段工作分解

### 阶段A：批准后的执行前检查

目标：建立本次实施时刻的真实起点。

1. 建立新的D盘证据目录，保存本次批准范围、北京时间、工作区、版本和未提交文件基线，保留所有旧记录。
2. 重新读取任务状态、动作、触发器、Principal、Settings与完整XML；权限不可读时标“未知”，不能推定无任务或已成功。
3. 检查当前正式根、材料、候选、新目标及祖先路径类型。拒绝恢复输入/目标中的链接和重解析点，不先resolve隐藏它们。
4. 确认任务不在Running/Queued；确认没有需保留的数据库WAL；出现WAL时停止，不能删除WAL或强制恢复。
5. 延用本地保守预算：可用物理内存至少2GiB、内存提交率不高于85%。该预算不是Windows故障阈值。
6. 确认目标不存在、D盘空间足以容纳新根及证据，进程TEMP/TMP使用D盘独立目录，不改全局环境。
7. 重新计算材料清单身份，调用现有材料和候选验证器，明确账本必须passed，不能接受not_present替代现有账本。
8. 保存本次完整清点。对于新增的预检比较，计划分别保存前后inventory及差异，以改善18日仅保留内存flag的证据限制。

还必须检查r04在18日材料形成后是否出现新的账本提交，不能只重复验证旧候选而忽略原正式根已经向前。先核文件指纹和归档；需要账本内容复核时，在既有双锁保护下制作新的审核副本，在副本中检查五表，不直接用数据库引擎连接原库。此类复制涉及源锁mtime，应在实施清单中披露并纳入批准范围。
若发现新增提交，或无法证明当前正式账本与批准候选相容，停止使用该旧候选，另建新编号恢复任务。数据库文件SHA变化也不能直接推断是行情还是账本变化，应先审核差异，不凭猜测放行。

不可变材料和候选只做只读重新校验，不向其中加锁文件或覆盖既有检查报告；例如材料复核使用record=False，新的结果保存在本轮证据目录。需要制作正式源审核副本时才取得源侧双锁，并明确其mtime副作用。

交付物：批准记录、执行基线、任务XML、资源/WAL/路径检查、材料及候选复核、五表身份、独立与交叉审查记录。

通过条件：身份与已批准候选一致、原始数据元数据完整、账本审核通过、没有并发冲突或资源阻断。

停止条件：路径漂移、来源变化、文件缺失/多出、SHA不符、账本差异、WAL、任务活动、资源不足或权限未知。停止后保留现场；只有新证据表明条件改变才安排新轮次，不循环盲重试。

| 层次 | 可接受的事实 | 不能据此直接推出 |
|---|---|---|
| 配置 | 动作与DataRoot正确、触发时间明确 | 系统一定会启动 |
| 系统 | 有实际启动时间和返回结果 | 应用归档与数据已成功 |
| 应用 | 有本次attempt/run身份、完成或失败状态 | 所有来源和日期都满足要求 |
| 数据 | 必需来源结果、完整性和实际覆盖日期可核对 | 账本必然已提交 |
| 账本 | 应处理日期与已提交事件一致、对账通过 | 策略有效或适合真实资金 |

返回码0是需要核对的必要信号之一，不能单独构成完整成功。系统与应用的对应关系若未证明，应明确“关联未核实”，不能只凭时间接近强配同一尝试。

失败必须保存失败步骤、错误分类、非零退出码及本次身份，区分market和ledger是否提交。不能把部分写入当作完整成功，也不能反向假定失败一定没有任何提交。

没有成交不自动判失败；允许无交易的有效运行，但仍需核对预期估值事件和报告。不应重复处理已有提交日期或重复创建待单。账户份额、现金、收益归因和基准日期等仍执行现有项目门禁，出现异常中止报告。

交付物应是一页可读结论加机器证据：本次是否启动、是否完成、来源是否满足、数据到哪天、账本提交了什么、尚有哪些问题。每次结论保留根路径和观察时刻。

### 阶段F：运行可靠性与状态检查完善

目标：在不触发行情的前提下，让“安排执行”和“实际成功”长期可区分。

已有只读状态入口、归档和账本检查作为优先复用对象；实施前先评估现状，不重复建设或默认全部已完工。拟核对的行为包括：

1. 分别展示计划时间、系统启动、最新应用尝试、最后成功、数据日期和账本估值日期。
2. 调度读取失败保留未知；权限不可读不显示为未运行或成功。
3. 最近失败与历史成功并列，旧成功不能盖住新失败。
4. 有启动而缺完成证据时突出未完成；不把它直接伪装成已确定的应用失败。
5. 显式输入预期日期，结合未到点、盘中、休市和日历覆盖范围判断。
6. 查询不同数据根时保留根身份，隔离状态明确可见；不为诊断初始化业务目录。

需要修改代码时再建立独立最小实现任务和有意义的隔离测试。优先测试权限失败、缺归档、部分提交、旧成功、新失败、跨根、盘中/休市和路径漂移，不通过正式任务跑测试。

### 阶段G：运营稳定性复核与研究交接

建议把连续5个“按日历与配置应执行的自然窗口”作为运维复核观察段，记录所有成功、失败、延期和有依据的跳过，不只挑成功日。该段是待批准的运营观察安排，不是现有策略门禁的新参数。

通过标准可定义为：没有未解释的漏启动或缺完成证据；来源失败均明确传播；数据预期与实际覆盖可解释；账本无重复提交和对账差异；状态入口能准确显示失败与未知。失败后保留全部记录并重新评估，不删除失败来制造连续成功。

运营观察达标不意味着研究完成。继续研究前必须读取已有experiments记录、固定新实验编号与参数，先运行manifest并记录数据集ID、SHA、来源、区间与陈旧状态。

既有历史只能作为回顾性稳定性诊断；不得重新包装成全新样本外证据。20、60、120、252个收益观察里程碑只能从已提交估值事件重建，不是策略有效或真实资金准入结论。

本阶段不调策略参数、不改样本切分、不引入新来源或现实费率结论，不修改已有模拟盘风险阈值。

## 七、风险、停止与回退

| 风险或现场情况 | 处置原则 |
|---|---|
| 资源不足或磁盘空间不足 | 停在写入前，保存观察；不提高门槛，不自动结束其他应用 |
| 任务活动、锁冲突或WAL | 停止并保留现场，不删除锁/WAL，不强制恢复 |
| 候选ID、SHA、元数据或来源漂移 | 不切换，定位差异并重新形成候选/审批身份 |
| 新根激活中断 | 保留半成品和失败状态，不交给正式任务，不覆盖重试 |
| 调度权限不可读 | 标未知，不将未读到解释为未执行；先解决证据缺口 |
| 系统有启动、应用缺完成 | 显示未完成/待核查，检查归档与提交事实，避免重复执行 |
| 来源失败而旧数据可读 | 保存旧快照但保留本次失败，不推进依赖成功的报告 |
| 账本出现负现金、非整数份额、重复事件或归因残差 | 中止报告，保存两侧证据，禁止人工改账掩盖 |

| 参数或研究范围被临时扩大 | 拆为新的研究/实施任务，当前切换停止扩张 |

回退不是无条件恢复原动作。必须先确认任务非运行态，并判断新根是否有新增账本提交：

回退同样继承阶段C的安全窗口要求，执行前重核即时资源/磁盘、任务活动、两侧WAL/路径、尝试身份和两侧提交边界；动作落地后以及回退交付前再核这些身份与提交边界。非运行态快照不是互斥保证，不能只检查一次就放行。
若中途启动、身份或提交变化、证据不可读，应停止后续双向切换并保存两侧证据，先确定实际使用根再对账；不擅自再次切换、杀进程或补跑。没有可核实安全窗口时停止变更，受控暂停/恢复调度仍须另行批准。

- 无法确定是否提交：按未知处理，不假定没有写入；先补齐证据，不做盲目重跑或覆盖复制。

状态措辞统一为以下可核实表达：

- “候选离线校验通过，未激活”；
- “新根验收完成，尚未切换任务”；
- “任务动作已切换，自然执行待验收”；
- “系统已启动，应用完成证据待核查”；
- “本次失败，失败步骤与已提交边界如下”；
- “本次成功，处理日期、数据集身份与账本提交如下”。

4. 后续运营观察安排及其授权状态。
