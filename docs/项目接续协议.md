## 每项任务的方向与证据检查

| 必答问题 | 合格记录 |
|---|---|
| 为什么做？ | 原阶段目标、用户决定或已确认缺陷的链接 |
| 做到哪就停？ | 本批验收标准，不能通过不断增加小任务把旧窗口无限延长 |
| 什么已获准？ | 批准对象/范围；一次例外与长期要求分开 |
| 实际做到哪？ | 主区已接入、独立候选、仅分析、待实施分别记录 |
| 什么证明通过？ | 测试/运行/数据/提交/审查证据及观察日期，不能只写“完成” |
| 什么还未知？ | 缺证、未测组合、未覆盖时段、权限跳过与风险限制 |

## 双重审查

两位审核者先独立审查，再互相核对结论。A侧重原目标、授权与阶段范围；B侧重实现或文档与证据一致性；两者都能提出范围或技术问题。实施者修复实质问题后，按改动运行必要验证，不重复无关或已通过的测试。

审查记录必须区分“方案可行”“实现通过”“实际已部署”“自然运行已验收”。如果只有代码测试，就不能批准运行结果；如果只有一次运行，就不能认定长期稳定。

## 压缩、暂停和交接

在可控的阶段边界更新task_plan、progress和当前状态：保存最新授权、已完成证据、候选/正式位置、未决问题、下一步及禁止重复动作。无需知道或控制每次自动压缩发生的时刻；每次接续仍从这些持久文件核对。

摘要仅作导航。决定存在争议时查原始对话备份；状态存在争议时查具体批次证据或进行当前只读观察。无法恢复的内容写明缺失，不补造原话。

暂停不等于任务达成，过期窗口不补记完成。新的“继续”按当时上下文恢复获准事项；不能把旧目标自动唤醒消息当新的人类授权。
