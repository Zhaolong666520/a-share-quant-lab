## 三批新增能力如何读取

### 独立只读状态汇总与运行身份

```powershell
.\.venv\Scripts\python.exe -B -m finance_lab.paper_operational_status --root . --portfolio default
```

`--root` 和 `--portfolio` 都必须明确填写。结果为 JSON，分别解释最近运行记录、最后有效成功、
行情发布/来源、账本最后估值及报告生成记录。退出码 `0` 为记录检查通过，`1` 为需注意，`2` 为请求错误。
旧字段或缺失归档保留未知，不从日期、最新行或文件名猜测事实，也不跳过较新的坏归档。

10 月 5 日追加的 schema2 **运行归档**保存独立 `attempt_id` 和实际提交收据；这与数据库账本 schema 版本是两个概念。
收据来自实际事务行，严格只读入口精确核对历史引用：`verified` 为完整关联，`partial_verified` 为已确认部分关联，
`no_new_commits` 为无新增，`mismatch` 为明确不匹配；旧归档或缺少收据保持未知/不可验证。
部分关联不代表整次成功，报告失败也可能已成功记账，不能据此重新初始化或自动重跑。

身份在最终归档才持久化；提交后、归档前强制终止仍可能缺证。此工具不生成报告、不补目录或锁，
不重新计算当前数据健康，不检查报告文件，不证明调度器正在运行。

### 运行前基线与运行后完整区间

```powershell
.\.venv\Scripts\python.exe -B -m finance_lab.paper_run_acceptance capture --root C:\quant\recovered --portfolio default
.\.venv\Scripts\python.exe -B -m finance_lab.paper_run_acceptance verify --root C:\quant\recovered --portfolio default --baseline C:\quant\evidence\before.json --attempt-id 第一次完整attempt_id --attempt-id 末次完整attempt_id
```

这些路径和 ID 都是示例。先按[证据保存步骤](恢复验收与研究会话.md#三每日模拟运行的区间验收)检查 capture 退出码，
将成功输出的 JSON 以 UTF-8 无 BOM 保存到业务根之外，再进行获批的模拟运行。工具本身不写证据文件，也不执行每日运行。
capture/verify 的 `--root` 必填，`--portfolio` 默认 `default`；建议显式传入实际账户组。

verify 必须按发生顺序重复 `--attempt-id`，列出基线之后**全部新归档**的完整 32 位 ID，而非只挑成功记录。
它保护五张账本表的既有历史，核对实际新增提交与收据完整、唯一对应，并要求正常 processed 后，
以同一 `as_of_date` 的末次 complete 空收据 no-op 收尾。失败、部分完成、缺证或未归档提交均不通过。

capture 成功退出 `0`；verify 的 `passed` 退出 `0`，`attention` / `unavailable` 退出 `1`；
非法参数或基线协议错误退出 `2`。`passed` 仅证明记录中的自动化与账本区间，不证明真实进程退出码、
实时行情健康、持续调度或报告 artifact 完整性。后续新批次应重新捕获基线，不截取旧区间冒充完整验收。
