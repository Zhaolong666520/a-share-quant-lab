# 运行验收与迟到诊断

运行诊断沿用 `python -m finance_lab.paper_runtime_status`，新增可选参数
`--expected-start-at 2026-10-26T18:30:00+08:00`。必须同时明确
`--expected-as-of 2026-10-26`，且计划时刻的北京时间日期与预期日期一致。
省略计划时刻时，迟到判断为未知；程序不把当前任务配置倒推为历史计划。

| 字段 | 含义与限制 |
|---|---|
| `schedule.expected_start_at` | 人工明确指定的计划时刻，不代表程序验证了交易日历或历史任务配置 |
| `schedule.system_last_start_at` | 系统记录的最新启动；可能来自其他日期或手动启动 |
| `schedule.state` | `not_due`尚未到点、`on_time`等于计划时刻、`delayed`晚于计划、`start_not_observed`未观察到目标时刻之后的启动、`unknown`证据不足 |
| `schedule.delay_seconds` | 仅目标日期且触发来源明确为时间触发时计算；不设置隐含容差，不以应用开始时间代替系统启动 |
| `application.latest_archived_attempt` | 最新有效应用归档及其开始/完成时间；失败不会被旧成功覆盖 |
| `report_json.state` | 最新归档指定JSON的字节SHA、身份、日期和最后处理日收据是否匹配；不能用latest报告路径替代缺失历史文件 |
| `report_json.data_end_date` | SHA绑定日报中声明的实际数据末日，不是请求截止日，也不是本轮重新读取行情得到的结论 |
| `report_json.unchecked_earlier_receipts` | 多日处理时，日报只包含最终账户状态，早日收据未由该文件独立重验 |
| `progress.last_valuation_date` | 既有账本检查提供的估值日期，与数据日分别展示 |

计划时刻尚未到达时，应用/估值日期落后该预期日显示`not_due`，不报该日漏跑。
其他真实失败、未知和数据来源warning继续保留。最新系统记录属于更晚一天时，
不会推断早日是否准时；手动/未知来源也不会获得自然准时结论。

`report_json`只验证一份不可变JSON：缺失、超限、越界、链接、损坏、SHA不符、
账户身份/日期冲突，或者观察期间输入变化，均不宣布核验通过。
no-op没有本次新增收据时明确标为`not_applicable_no_new_receipts`，不虚构核验数。

即使JSON匹配，也不表示HTML/图片都验证过，更不表示数据库事件已独立核实。
系统实例与应用attempt仍没有共同身份绑定时，
`scheduler_application_correlation`和`natural_run_acceptance_verified`保持原有保守值。
运行成功不等于来源充分；现有95%覆盖门槛和来源警告保持原样。

现有完整诊断入口会对指定根中的数据库进行只读检查；`--no-scheduler`只关闭系统查询，
不会关闭账本检查。本次开发验证使用隔离合成夹具；正式根只执行文件级证据核验。
新增纯时间计算与JSON核验模块本身不连接数据库，不触发任务、不请求行情、
不更改系统电源，也不注册后台检查或提醒。
