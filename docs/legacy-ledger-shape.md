# 旧版账本缺表与迁移边界

日期：2026-11-06。本文说明 P1 隔离候选的行为，不表示已部署到正式任务。

`PaperStore.ensure_schema()` 在创建或升级任何账本表之前，检查现有 `paper_` 对象和版本记录。完整的 v1 账本包含版本元数据、账户、运行、事件和状态五张表；其迁移必须在同一事务内完成结构校验、事件重放和账户对账，成功后才提交。

## 允许与拒绝

| 输入 | 行为 |
|---|---|
| 没有账本对象（可有行情表） | 初始化新账本，保留其他表 |
| 仅版本元数据，版本记录为空或为 v1 | 保留既有初始化行为；本次增加正向测试 |
| v1 元数据和状态表，其他账本表都不存在 | 保留既有状态片段兼容，补充权益记录字段；不是完整历史证明 |
| 完整 v1 账本 | 结构迁移后审计完整历史；任一步失败则回滚 |
| 其他不完整 v1 业务表组合 | 创建表之前明确拒绝，禁止补空表并升级版本 |
| v2 缺表或结构错误 | 沿用严格结构检查，禁止自动补齐 |
| 缺少版本元数据、空版本配合业务表、未知或重复版本 | 沿用现有拒绝规则 |

状态片段兼容包括旧表缺少权益记录字段，以及迁移中断留下可空权益记录字段的既有格式。兼容迁移不改变原有现金、持仓和事件身份；没有账户和历史事件的孤立状态仍会被完整恢复审计拒绝。

## 已确认的问题与修复

旧逻辑只对迁移前已具备全部五张表的 v1 账本安排历史审计。其他缺表组合可能先被 `CREATE TABLE IF NOT EXISTS` 补齐，再写入 v2 版本，跳过完整历史审计。后续业务入口即使拒绝，也无法撤回已经提交的结构变更。

本次在 DDL 之前增加 v1 表集合检查，只保留完整账本和上述既有初始化、状态片段路径。不修改格式版本、事件哈希算法、策略或正式数据。

## 验证与限制

专项测试枚举四张业务表的 13 种不受支持的非空真子集，各覆盖空数据和非空数据，共 26 个场景。修复前均复现结构或版本被改变；修复后均拒绝，表、列、约束、全部行、版本和行情哨兵保持一致。另验证 v2 四种单表缺失、元数据初始化、片段与完整审计的区别，以及真实 DDL 和历史审计完成后注入异常的整体事务回滚。所有破坏操作仅针对新建合成夹具。

仅凭表集合，无法区分合法元数据或状态片段与某些多表丢失后的相同残留。因此本修复不声称识别任意缺表损坏；元数据空账本审计通过也不能证明它曾经没有历史。需要完整历史证明时，应使用恢复审计并核对来源和先前快照。

本批未打开或迁移正式数据库，未证明正式数据具有或不具有上述问题。验证使用本机既有 Python/DuckDB 环境；测试结果及平台限制见本批证据报告。
