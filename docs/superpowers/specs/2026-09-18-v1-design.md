# A-Share Quant Lab v1.0 设计方案

日期：2026-09-18。性质：分阶段建设方案；写入方案不代表功能已经交付。

## 1. 目标与完成定义

面向不会编程的个人学习者，提供一个能安装、能解释数据状态、能复现实验、能持续记录模拟账户、出现故障能恢复的本地日线研究工具。

用户应当能够完成以下闭环：

```text
安装与离线演示 → 核对数据健康 → 阅读固定实验与风险解释
                              → 每日模拟记账 → 查看统一工作台
                                               ↓
                                      失败留证与安全恢复
```

v1.0 的“完成”以本方案的验收证据为准。策略收益高低不作为软件质量验收条件，演示与真实数据必须清楚区分。推广、Star 增长和新策略数量不属于本轮交付目标。

## 2. 当前基线与缺口

本次检查基于本地 `codex/v1-quality-sprint` 分支、起点提交 `0b16aa3`。本地版本声明仍为 0.9.1；四轮质量改进已有四个本地提交，不等于已合并、已发布或当前云端 CI 已通过。

| 领域 | 当前代码已有 | v1.0 需要补齐或重新验证 |
| --- | --- | --- |
| 数据 | AKShare 指数/ETF 日线、BaoStock 核对、Parquet、DuckDB | 写入中临时文件隔离、标的身份一致性、并发与批次一致性 |
| 可信度 | 数据指纹、来源/单位/复权、陈旧度、交易日历 | 数据源异常契约、不可解析文件处理、日历覆盖期提示 |
| 研究 | 固定切分、walk-forward、成本/参数/执行压力、账户回测 | 保护现有无未来数据和成本归属测试，统一产物入口 |
| 模拟盘 | 双账户、事件哈希链、事务迁移、锁、订单状态、收益归因 | 非空旧账本迁移矩阵、结构约束核验、恢复演练 |
| 使用 | Windows 入口、跨平台离线 demo、HTML/JSON/CSV 报告 | 安装包实际业务冒烟、错误指引、统一只读工作台 |
| 运行 | 每日执行与成功/失败状态、计划任务安装/卸载脚本 | 当前安装状态清点、重复运行/断网/中断验收、备份恢复 |
| 质量 | Ruff、mypy、覆盖率门槛、依赖审计、打包与链接检查 | 增强关键故障测试，区分本机结果和 CI 矩阵结果 |

2026-09-14 的历史验收记录为 393 个测试通过、开启 branch 测量后的综合覆盖率 83.28%。当前配置的 80% 是语句与分支的综合覆盖率门槛，不是单独的分支覆盖率。本次及以后均重新记录实际结果，历史通过不能代替当前验证。

设计起点发现的具体问题（完成状态见第 8 节）：

1. Parquet 临时文件名以 `.tmp.parquet` 结尾，三处 `glob("*.parquet")` 会把它读入；尚未写完时会报错，写完未发布时可能重复统计。
2. `save_curated` 和 `read_curated` 尚需补充单标的身份及文件映射一致性约束；点号替换下划线存在别名碰撞风险。
3. 单文件原子替换不等于多个行情文件与摘要组成一致快照，也不等于机器断电后的持久性保证。
4. 模拟账本已有事务与表列检查，仍须验证字段类型、空值、主键与约束，不应笼统宣称所有结构都已验证。
5. wheel 冒烟目前只验证导入及 `--help`；源码定位默认根目录的方式和随包配置需要实际业务测试。
6. 真实数据源当前可用性、现有计划任务是否启用、实际累计模拟天数，本次设计阶段未联网或运行账户确认。

## 3. 方案选择

| 路线 | 优点 | 代价 | 决策 |
| --- | --- | --- | --- |
| 先可靠性，再运行体验与界面 | 每一步能用测试证明，界面基于可信数据 | 初期可见页面变化少 | 采用 |
| 先做大型交互界面 | 很快能看到新页面 | 数据/账本问题仍会影响页面结论，后续返工面大 | 工作台延后到第四阶段 |
| 先扩展分钟行情、多资产和自动选股 | 功能列表增长快 | 新数据授权、交易语义和验证范围大幅增长 | 移出 v1.0 |

延续 Python、pandas、Parquet、DuckDB、现有 CLI 和本地 HTML 报告。前三阶段不增加服务端或前端运行时依赖。工作台采用静态本地 HTML 与汇总 JSON，不启动公网服务；交互式参数编辑和常驻 Web 服务属于后续独立方案。

## 4. 范围与全局约束

- Python 支持范围维持 `>=3.11,<3.14`。
- 现有 CI 综合覆盖率门槛保持 `80%`；关键新增故障分支必须有针对性测试，不通过扩大排除范围提高数字。
- 保留现有 `symbol, trade_date, open, high, low, close, volume, volume_unit, amount, adjustment, source, ingested_at` 日线契约。
- 真实数据来源维持 AKShare 与 BaoStock；增加来源、购买数据、录入密钥前单独确认。
- 初始配置保留 `sh.000300` 指数和 `sh.510300` ETF；固定前向模拟盘仍为 ETF 的 SMA 20/60 与 120 日动量两个隔离账户。
- 原始快照及事件账本保留；迁移不得覆盖原始行情、重置账户、丢弃历史事件或删除亏损实验。
- 策略信号至少延迟到下一交易日；样本外结果查看后的参数与切分不在原实验中更改。
- 负现金、非整数份额、哈希链异常和超过 `1e-6` 元的逐日归因残差必须阻断相关报告或提交。
- 所有费用、滑点与日线成交阻塞代理维持现有假设标签；不引入未经核实的交易所实时规则。
- 本轮仅修改本地开发分支；不自动推送、合并、发布、安装计划任务或连接券商。
- 测试使用隔离临时目录和清楚标注的合成数据；不运行或改写用户现有模拟账户。
- 没有执行的验收标为“未验证”，网络失败、缓存陈旧与真实成功分别呈现。

v1.0 不包含：实盘自动交易、收益保证、分钟/Tick 行情、跨市场组合优化、机器学习自动调参、付费数据市场、多 AI 常驻编排、跨代码公司行动和零碎份额登记分配。

## 5. 模块职责与接口边界

| 层 | 现有位置 | 设计职责 |
| --- | --- | --- |
| 采集适配 | `src/finance_lab/sources.py` | 外部接口转换为规范日线；缺字段、空结果、上游失败明确报告 |
| 发布与存储 | `atomic_io.py`、`storage.py` | 临时写入、完整文件发布、不可变快照、整理数据与数据库同步 |
| 数据健康 | `validation.py`、`data_manifest.py` | 日期/价格/元数据约束、文件指纹与陈旧度；健康结果携带依据 |
| 研究 | `pipeline.py`、`experiment.py`、各诊断模块 | 显式接收参数、固定输入身份、复用计算与报告流程 |
| 模拟账户 | `paper_engine.py`、`paper_store.py`、`paper_pipeline.py` | 事件为事实来源；状态可重建；提交与报告失败严格区分 |
| 运行 | `paper_automation.py`、`cli.py`、`scripts/` | 调用上述能力、返回可靠状态/退出码、提供恢复操作指引 |
| 展示 | 现有报告模块；拟增加 `workspace_report.py` | 读取产物和状态，形成统一导航；不重算交易，不修改账户 |

首个新增接口为 `atomic_io.published_parquet_files(directory: Path) -> list[Path]`，用于数据库同步、数据清单和数据校验三处枚举。

发布协议：新临时文件使用 `.<正式文件名>.<uuid>.tmp`；只有发布后才具有正式 `.parquet` 后缀。为兼容历史中断残留，枚举忽略保留的 `.*.tmp.parquet` 临时命名空间，但保留文件供诊断，不清理、不改名。其他 `.parquet` 文件一律正常读取并校验；正式文件损坏仍报错。

后续存储阶段需要建立统一写锁/批次版本协议。验收目标是在并发更新时读取完整旧批次或新批次，或明确拒绝重试，不能返回无标识的跨批次混合结果。第一项临时文件隔离只解决文件可见性，不承担此完整协议。

## 6. 分阶段设计与验收

### P0：设计与基线（本次）

交付此方案、独立第一步实施计划和可追加的验收记录。记录当前分支及提交，不更改项目版本、不对已有账户作“无历史数据”等未经核实的判断。

通过条件：每个阶段有范围、依赖、交付物、失败处理和可执行验收目标；第一步可单独回归。

### P1：数据与账本可靠性

按三个独立小批次执行，每批次先写能够失败的测试：

1. **P1.1 临时文件隔离**：两个 Parquet 写入入口改用 `.tmp`，三个消费者共用枚举接口。覆盖写入中、完成未发布、历史残留、只有残留、正式文件损坏、替换失败、原始快照冲突。
2. **P1.2 数据身份与并发**：限制一份整理文件只能承载一个规范标的；写入前后核对文件与 payload；明确历史名称兼容策略。覆盖混合标的、别名/大小写碰撞、越界路径、两个同时更新进程和跨批次扫描。对可能影响历史数据的迁移先输出只读检查结果，禁止自动重命名。
3. **P1.3 账本结构与恢复**：建立受支持 schema 版本和完整结构的测试矩阵；对非空旧账本验证迁移前后事件、哈希与权益相等。未知未来版本、缺约束、错误类型及中途异常均不得产生部分迁移。

交付：存储与账本故障回归测试、兼容规则、迁移/拒绝信息。退出条件：上述场景逐项有证据，原始文件和历史事件不受损。P1.2 与 P1.3 分别形成自己的小型设计和执行计划，不在 P1.1 中顺带修改。

### P2：接口、CLI 与安装可验证

1. **P2.1 数据源契约**：使用本地响应样本验证成功、空数据、缺字段、数值异常、超时、登录/查询失败、退出清理。mock 只放在外部接口边界。记录收到/接受/拒绝行数，不把丢行当作完整成功。离线契约测试与可选的真实联网检查分别标注。
2. **P2.2 命令失败语义**：逐项验证现有命令的非法日期/参数、缺文件、损坏文件、写入失败；失败非零退出，说明失败步骤、数据是否已提交和下一步操作，不能靠输出一段 JSON 就算成功。
3. **P2.3 安装包业务冒烟**：在仓库之外创建干净环境安装 wheel，设置隔离的 `FINANCE_LAB_ROOT`，实际运行 demo 并验证 HTML/CSV/JSON。核验初始化配置与日历资源随包可用，默认路径不写进 site-packages。先确定初始化契约再实施，保留源码运行兼容性。

交付：可复现的安装测试、接口契约样本、故障对照表。Windows Python 3.11/3.12/3.13 全套现有质量任务必须通过；Linux/macOS 离线 demo 继续验证。没有验证的组合不宣称支持全部研究与计划任务。

### P3：每日模拟运行与恢复

1. **P3.1 状态一致性**：将更新、健康、记账、报告分步结果关联到同一个运行身份。重复运行不重复记账；报告失败时保留已提交账本，明确报告待重建；上游失败保留最后一次成功日期，但本次状态为失败。
2. **P3.2 隔离恢复演练**：在临时目录复制测试账本，验证备份清单/校验和、事件重放、报告重建。恢复必须使用新目录，核对事件数/哈希/现金/份额/权益一致后才允许人工选择切换。Windows 的关闭文件或一致性快照要求写入操作手册。
3. **P3.3 运行验收记录**：只读清点实际计划任务与状态；真实运行使用稳定项目目录，安装或修改时间单独确认。离线场景覆盖正常、断网、陈旧、重复、锁冲突、账本提交后报告失败以及历史残差超限。

交付：运行状态说明、恢复脚本/步骤、隔离演练结果、真实观察记录模板。实际观察次数从已提交事件重建；保留 20/60/120/252 日里程碑，不用重放生成的历史天数代替真实运行观察。

### P4：本地可视化工作台

目标：打开一个入口就知道数据新不新、今天有没有运行、报告在哪里、失败后怎么办。

新增静态 `outputs/workspace/index.html` 及同目录汇总 JSON（实施时生成，不在本次创建）。配套一个 CLI 生成入口与 Windows 双击入口；名称/参数在本阶段的独立实施计划中固定。页面默认离线可读，不下载外部脚本、字体或分析追踪资源。

页面顺序：

1. 顶部：项目版本、工作台生成时间、数据截至日、本次运行状态、最后成功日期。
2. 数据卡片：标的、来源、采集时间、陈旧度、数据集 ID、缺失/错误原因。
3. 模拟卡片：两个账户现金/持仓/权益、累计与当前回撤、实际观察数、样本不足说明。
4. 研究报告列表：实验编号、参数、区间、成本口径、数据身份和详情链接，包含负结果。
5. 故障区域：失败步骤、是否已提交、日志与可操作的恢复指引。

展示契约：只读取受验证的汇总和报告元数据；缺字段显示“未知/需重新生成”，不按 0 填充。损坏或不受支持版本的 JSON 显式告警。禁止从文件名推测收益；链接限制在项目产物目录内，文本进行 HTML 转义，拒绝可执行 URL。旧工作台需展示生成时间，避免截图被误认实时状态。

验收：空目录、只有 demo、正常双账户、数据陈旧、上游失败、报告失败、JSON 损坏、历史不足八类页面；320px 与桌面布局无主要内容遮挡；键盘可访问链接；中文路径可打开；账本文件内容与事件不因生成工作台而改变。

### P5：v1.0 发布候选验收

1. **P5.1 统一质量证据**：完整测试、Ruff、mypy、编译、依赖一致性、Markdown 链接、依赖漏洞审计、源码包与 wheel 业务冒烟均留存日期、命令、环境、提交和结果。联网审计失败标记未完成。
2. **P5.2 新用户验收**：从干净目录按文档执行安装、demo、健康查看、模拟测试场景、工作台和恢复演练。维护一份“已测/未测”平台矩阵，核对 README 与行为一致。
3. **P5.3 候选冻结**：没有未关闭的数据损坏、账本错误、未来数据使用等高严重性问题；已知限制可定位到文档；用户确认后才创建 PR、合并、打标签或发布。

性能先测现有固定合成样本规模与耗时、峰值内存，再根据实际瓶颈约定预算；不在没有基线时承诺速度。覆盖率提升以风险场景为依据，v1.0 最低保持现有 80% 综合门槛，核心资金/发布/迁移分支逐项有测试。

## 7. 故障处理矩阵

| 故障 | 程序行为 | 用户恢复方式 |
| --- | --- | --- |
| 写入过程异常 | 保留上一正式文件；可控异常清理本次临时文件 | 查看原因后重新更新 |
| 进程强制终止留下临时文件 | 读取时忽略保留临时命名空间；不自动删除 | 保留证据，另行清点 |
| 正式行情损坏/身份不符 | 明确报错，不能跳过并宣称完整成功 | 核对原始快照与指纹，在新目录重建 |
| 跨进程锁冲突 | 非零退出并保留持锁运行 | 等待运行结束后重试；不随意删除锁 |
| 旧账本迁移失败/未来版本 | 拒绝操作，事务回滚 | 使用匹配版本，在副本中诊断 |
| 数据源失败/日历超出覆盖期 | 保留失败原因，阻断依赖新行情的模拟运行 | 修复来源或经核实更新日历，再运行 |
| 提交完成但报告写入失败 | 不撤销账本；记录报告失败 | 重建报告，不能重新创建当日成交 |
| 备份不一致/校验失败 | 不切换、不覆盖原账户 | 查找完整备份并在隔离目录再次核验 |

## 8. 执行节奏与进度
