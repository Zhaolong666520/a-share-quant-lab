## 1. 已核对的风险

当前 `pipeline.update_market_data` 在项目行情锁内依次获取各标的、保存原始快照和整理行情、同步 DuckDB，最后原子发布 `outputs/update_summary.json`。

原子发布保护的是一个文件：摘要写入失败时旧摘要仍在，但先前写入的整理行情或数据库不会自动回滚。进程退出会释放锁，后续读取可能重新放行。旧摘要存在、单文件校验通过，都不能证明上一次整批更新完成。

此结论来自本次代码检查，不是对用户现有数据已经损坏的判断。本轮不运行真实更新、不修改现有行情与模拟账户。

## 2. 路线比较与建议

| 路线 | 得到什么 | 代价与风险 | 本步选择 |
| --- | --- | --- | --- |
| 持久状态标记＋阻断＋只读诊断 | 中断后不再静默使用不完整批次；保留文件供检查 | 中断后要先修复，不能继续正常计算 | 推荐，先做这一小步 |
| 自动备份并回滚 | 失败后可尝试恢复旧数据 | 恢复也可能中断；共享数据库含模拟账本，不能整库回滚 | 后续单独设计，不直接实施 |
| 不可变批次目录＋版本指针 | 消费者固定读取完整版本 | 需要迁移路径、读取协议、数据库同步与旧项目兼容 | 长期候选，不在本步重构 |

建议采用第一条。接受的取舍是：宁可让本次研究/模拟任务明确失败，也不自动覆盖旧文件或把未完成更新认作可用数据。恢复方案完成前，受影响项目保持隔离，不提供“强制忽略”或“删标记即可恢复”的指导。

## 3. 状态与发布规则

拟新增 `data/market_update_state.json`，与 `data/market_data.lock` 分工不同：锁处理正在运行的竞争，状态文件在进程退出后继续记录批次是否完成。运行时文件不进入 Git。

状态结构使用版本号，至少记录批次 ID、请求日期区间、配置标的、开始时间、发布阶段；完成状态额外记录完成时间及本次更新摘要的 SHA-256。错误记录只保留必要的错误类型和阶段，不包含凭证或上游完整响应。

| 状态 | 含义 | 消费者行为 |
| --- | --- | --- |
| 文件不存在 | 尚无新协议记录的旧项目 | 保留原有校验行为，不声称历史批次已受保护 |
| `updating` | 更新开始后尚未完成；即使原进程已退出也成立 | 阻止正常行情消费与新的更新 |
| `failed` | 捕获到更新异常 | 与 `updating` 同样阻断，保留证据 |
| `completed` | 本次发布流程已走完，摘要与状态匹配 | 继续现有内容、身份、日期与来源健康校验 |
| 损坏、缺字段、未知版本/状态或摘要不匹配 | 无法证明状态可靠 | 明确阻断，不能当成“没有标记” |

顺序约束：

1. 获取现有行情锁，检查已有状态。未完成或异常状态不能被新任务覆盖。
2. 验证日期、配置等前置条件，原子写入 `updating`，然后才允许抓取与修改行情产物。标记创建失败时不得开始更新。
3. 执行原有获取、快照保存、整理、数据库同步和摘要发布。批次内部的合法写入受本批次上下文约束；不能仅因“当前线程持锁”就绕过未完成状态检查。
4. 摘要发布完成、指纹读取成功后，最后原子写入 `completed`。若完成状态写入失败，仍保留阻断状态。
5. 捕获异常时尽力写入 `failed`；失败状态写入也失败时保留之前的 `updating`，不掩盖原始异常。不在 `finally` 中无条件移除标记。

`completed` 只表示“本次发布结果已完整记录”，不表示数据源全部成功、数据新鲜或策略可用。零成功标的、来源错误、缺少数据等仍保留原有错误记录和下游门禁，不能被状态文件洗成成功。

本步目标为进程中断和普通 I/O 异常，不承诺机器断电、磁盘损坏后的持久性保证；若要增加此保证，需要另行设计和验证文件/目录刷盘协议。

## 4. 模块与入口

拟新增 `market_data_state.py`，负责严格解析、状态发布、可读性检查与专用异常；复用 `market_data_lock` 和原子文件发布，不混入交易逻辑。

`update_market_data` 负责批次生命周期。`read_curated`、清单生成、摘要正常读取、校验与模拟盘快照在同一行情锁内先检查状态。已有未完成批次时，独立的存储写入和数据库同步也拒绝操作，不能用单独同步或另一次窄日期更新绕过阻断。

所有依赖这些入口的新回测和模拟操作都会收到明确失败。历史静态报告不会被删除或修改，但它们只代表生成时的历史结果，不证明当前数据可用。

实施审查补充：旧版模拟估值事件的开盘价回填也需要当前行情，因此 `paper_report` 的该分支必须使用受保护的 `read_curated`。现代账本事件自带开盘价的历史报告不依赖当前行情，仍可生成；不因此放宽需要行情的路径。

拟新增只读命令 `finance-lab data-update-status`：不抓行情、不修复、不推进账户；报告状态、批次、请求范围、最后记录阶段及下一步人工检查提示。它必须能诊断异常状态而不走正常消费者的拒绝入口；取得锁后读取，繁忙时提示重试。健康/兼容旧项目返回 0，未完成或无法解析返回非零。

CLI 普通命令沿用非零退出机制；每日自动化沿用失败步骤与不可变运行归档，失败后不能继续模拟记账。本步不自动重试，也不新增定时任务。

下一小步 P1.2b.2b 再定义修复来源、覆盖范围、配置变化、恢复再次中断和人工切换协议；修复不得回滚共享数据库中的模拟账户历史，也不得修改原始快照。只有验证通过的恢复流程才能解除隔离。

本步也不解决：手工删除/篡改状态、绕过项目 API 的程序、协议引入前的历史中断、独立成功存储调用组成的跨文件事务，以及分开多次 API 调用之间的研究快照绑定。不得把本步宣传为完整的跨文件一致性解决方案。

## 6. 验收设计

先编写能暴露旧行为的测试，再最小实现；合成行情与临时目录隔离，不运行真实行情或用户账户。

- 标记创建失败：尚未抓取或修改行情，旧文件不变。
- 第一份整理行情发布后失败：锁释放后读取、清单、校验、模拟、新更新和独立写入仍拒绝，不产生新账户事件。
- 数据库同步失败、摘要发布失败、完成标记发布失败：均不能被当成成功批次。
- 捕获异常后的失败标记写入再次失败：仍保留阻断依据和原始异常。
- 子进程在关键发布边界强制退出：新进程获得锁后仍检测到未完成状态。
- 损坏标记、未知版本、字段错误、摘要指纹不符：不能退化为无标记兼容路径。
- 无状态文件的旧项目：原有身份和健康检查继续工作，不伪造历史完成记录。
- 正常完成及来源失败：发布状态与业务健康分开验证，错误不得丢失。
- 只读状态命令与每日自动化：明确退出码、失败步骤；诊断不得改变行情、账本或状态文件。
- 再跑并发测试、全套回归、Ruff、mypy、编译、依赖及文档链接检查，核对用户现有文件指纹不变。

本批测试结果单列在实施记录中；上一批 507 项测试通过属于历史验收，不代替本批验证。
