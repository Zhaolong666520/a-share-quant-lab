# P1.2b.2c.1：单份研究报告的行情快照边界

## 风险与范围

单份研究报告可能先读取已发布行情，再计算和写入文件。若项目级行情锁只覆盖其中一次读取，另一个进程可能在后续步骤更新行情，使报告生成过程跨越两代数据。已有账户/对比报告的文件哈希检查只能覆盖检查时点，不能阻止之后的更新。本批只处理单次研究与健康报告调用；多标的批量命令之间的统一快照另行设计。

## 实施任务

1. 先用合成数据和并发线程复现研究计算阶段锁已释放，可插入行情操作。
2. 对所有单份研究报告入口和数据健康报告入口，从数据读取到报告发布持有项目级可重入行情锁；保留现有来源、数据隔离和写报告失败语义。
3. 验证同线程嵌套调用不死锁、竞争线程被明确拒绝、异常后释放锁。对代表性入口做并发测试，其他入口做覆盖检查。
4. 运行定向和完整测试、Ruff、mypy、Markdown 链接、差异检查；不使用真实行情或改动正式数据。

## 限制

此方案会让长时间研究计算暂时阻止同行情目录的更新；属于一致性优先的本地研究取舍，不代表对非协作外部写入者的保护，也不解决多个命令或多标的批次之间的快照一致性。

## 验证结果

先复现回测计算阶段竞争线程可以取得行情锁；实施后，数据健康、账户回测、普通回测、策略对比、样本外实验、滚动检验、成本压力、参数稳健性和执行可行性 9 个入口在输入读取时均拒绝竞争者。另测回测计算与报告发布阶段、位置参数 `root`、异常后的锁释放。11 项定向测试和完整 `pytest -q` 通过（1 项 Windows 符号链接权限测试跳过）；Ruff、mypy、77 份 Markdown 链接及 `git diff --check` 通过。全部是临时目录与合成数据，未联网获取行情。
