# P2.2z：行情更新中断十点故障矩阵

## 边界

使用临时项目和合成行情，对 `fetch` 与 `all` 各注入五种更新中断，共十个独立检查点。这里验证故障语义与持久化隔离，不抓真实行情、不执行交易，也不清除失败批次。

| 检查点 | 命令 | 注入位置 | 预期的持久化状态 |
| --- | --- | --- | --- |
| 1 | `fetch` | 初始状态发布 | 尚未进入抓取，旧整理行情与摘要不变 |
| 2 | `all` | 初始状态发布 | 同上，不启动回测报告 |
| 3 | `fetch` | 原始快照保存 | 批次失败隔离，旧整理行情与摘要不变 |
| 4 | `all` | 原始快照保存 | 同上，不启动回测报告 |
| 5 | `fetch` | 整理行情发布 | 批次失败隔离，旧整理行情与摘要不变 |
| 6 | `all` | 整理行情发布 | 同上，不启动回测报告 |
| 7 | `fetch` | DuckDB 同步 | 新整理行情可能已写入，旧摘要不变，批次失败隔离 |
| 8 | `all` | DuckDB 同步 | 同上，不启动回测报告 |
| 9 | `fetch` | 最终状态提交 | 新整理行情和摘要已写入，提交失败后批次隔离 |
| 10 | `all` | 最终状态提交 | 同上，不启动回测报告 |

## 修复与统一契约

真实 DuckDB I/O 异常属于 `duckdb.Error`，不是 `OSError`。`fetch` 和 `all` 现同时捕获 DuckDB、文件 I/O 与批次状态异常，输出安全的 `market_update_interrupted` JSON；底层路径与错误正文不外泄。所有中断均保守标记 `data_committed=null`、`summary_state=unknown`，并引导先运行 `data-update-status`。`all` 额外给出 `report_batch_complete=false`、`reports_confirmed=[]`，且绝不进入报告生成阶段。

## 验证

十个参数化故障用例全部通过。各检查点核对退出码、单个 JSON、状态阶段、隔离标志、整理行情/摘要字节、无底层错误泄露和无错误的报告完成提示。既有摘要写入失败测试继续保留。完整 pytest 通过（仅一个 Windows 符号链接权限相关测试跳过）；Ruff、mypy、Markdown 链接及 `git diff --check` 通过。

## 后续

此矩阵不证明操作系统断电时的持久化保证。每日自动化和更细的数据库事务恢复仍需独立验证；用户不得删除隔离标记来强制继续。
